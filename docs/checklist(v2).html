Level Up — High Priority (Must Have)
06
Code Quality — DTO, Validation, Logging
High
~1 tuần 0/6 ▾
Tạo Request/Response DTO cho tất cả API (Product, Category, Order, User) — không trả entity trực tiếp
Vì sao quan trọng: tránh leak cấu trúc DB, tránh lỗi lazy-loading khi serialize entity. Câu hỏi phỏng vấn kinh điển: "Tại sao không return entity luôn?"
Spring
Thêm Bean Validation (@NotBlank, @Min, @Email...) trên tất cả Request DTO
Vì sao quan trọng: chặn dữ liệu bẩn từ tầng API trước khi chạm business logic, giảm bug ở tầng service.
Spring
Cấu hình MapStruct (hoặc mapper thủ công) để convert Entity ↔ DTO gọn hơn
Vì sao quan trọng: giảm boilerplate, code sạch hơn khi số lượng entity tăng.
Spring
Thêm SLF4J logging tại các điểm quan trọng: request vào, quyết định business (tạo order, hết hàng, auth fail), exception handler
Vì sao quan trọng: câu hỏi "bạn debug production như thế nào?" cần có log thật để trả lời, không chỉ "chạy lại trên máy mình".
DevOps
Review lại toàn bộ exception handling, đảm bảo mọi lỗi đều trả JSON nhất quán (không lộ stack trace)
Vì sao quan trọng: lộ stack trace ra client là lỗ hổng bảo mật cơ bản, recruiter/senior review code sẽ để ý ngay.
Spring
Test lại toàn bộ API trên Postman sau khi đổi sang DTO, cập nhật Postman collection
Test
Tất cả API dùng DTO, có validation, có log — không còn entity nào bị expose trực tiếp
07
Testing & Reliability — Unit Test + Fix Race Condition
High
~1.5 tuần 0/7 ▾
Viết unit test cho Service layer (OrderService, CartService, ProductService) dùng Mockito mock Repository
Vì sao quan trọng: "Do you write tests?" gần như luôn xuất hiện trong phỏng vấn intern. Hiện tại checklist claim CI chạy test nhưng chưa có test nào thật — cần fix trước.
Test
Viết integration test với MockMvc + @SpringBootTest cho: login, tạo order, truy cập không có token
Vì sao quan trọng: chứng minh flow thật sự chạy đúng end-to-end, không chỉ test riêng lẻ từng hàm.
Test
Thêm @Version (optimistic locking) vào entity Product để tránh oversell khi 2 request đặt hàng cùng lúc
Vì sao quan trọng: đây là bug thật đang tồn tại (race condition khi trừ stock). Fix được là câu chuyện STAR rất mạnh cho phỏng vấn.
DB
Viết test giả lập 2 request đặt hàng đồng thời cho sản phẩm chỉ còn 1 stock, xác nhận không bị âm kho
Vì sao quan trọng: có bằng chứng cụ thể (test) thay vì chỉ nói miệng "em có nghĩ tới concurrency".
Test
Xử lý conflict trả về HTTP 409 khi optimistic lock fail, thay vì lỗi 500 chung chung
Vì sao quan trọng: thể hiện hiểu đúng HTTP semantics, không chỉ để exception mặc định leak ra ngoài.
Spring
Cập nhật GitHub Actions CI: chạy "mvn test" thật và fail build nếu test fail
DevOps
Có ≥15 test thật chạy trong CI, race condition khi đặt hàng đã được test và fix

Level Up — Medium Priority (Nice to Have)
09
Security & Performance — Refresh Token, Cache, Idempotency
Medium
~1.5 tuần 0/6 ▾
Đổi sang access token (thời gian sống ngắn) + refresh token (thời gian sống dài) + API POST /auth/refresh
Vì sao quan trọng: JWT không hết hạn hợp lý là câu hỏi phỏng vấn rất hay gặp ("token bị lộ thì sao?"). Có refresh token show hiểu biết đầy đủ hơn về JWT.
Auth
Test Postman: access token hết hạn → dùng refresh token lấy access token mới
Test
Thêm Spring Cache + Caffeine, @Cacheable cho GET category list và GET product by id
Vì sao quan trọng: thể hiện tư duy read/write tradeoff mà không cần hạ tầng phức tạp như Redis.
Perf
Ghi rõ trong README: cache hiện tại là in-memory (single instance), không phải distributed cache
Docs
Thêm header Idempotency-Key cho POST /orders và POST /payment/mock, lưu key đã xử lý để tránh tạo trùng đơn khi client retry
Vì sao quan trọng: retry gây trùng đơn hàng là vấn đề thật trong hệ thống thanh toán thực tế — ít intern nghĩ tới, là điểm khác biệt tốt.
Spring
Viết test: gửi lại cùng 1 request tạo order 2 lần với cùng Idempotency-Key → chỉ tạo 1 order
Test
JWT có refresh flow, có cache cơ bản, order/payment an toàn với retry trùng lặp
